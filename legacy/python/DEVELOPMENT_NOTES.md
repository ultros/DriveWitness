# DriveWitness modernization

## Repository audit

The original repository contained `drivewitness.py`, `requirements.txt`, README and a license. There was **no GUI framework, packaging metadata or test suite** to preserve. Windows drive discovery used `GetLogicalDrives` plus pywin32 volume/disk APIs. `os.walk` enumerated files; each file received an `os.stat`, an 8 KiB SHA-1 read loop, six zlib-compressed text fields and one SQLite insert. Commits occurred every 10,000 successful files, followed by a full `VACUUM`; completion vacuumed again. Two unversioned tables (`files`, `scans`) recorded observations without connecting files to individual scans.

Startup imported requests and three pywin32 modules. Network time was one synchronous, ten-second HTTP request before collection. The machine identifier hashed three environment strings. UUID anonymization changed on each run, left the complete original path recoverable, and offered a dictionary-recoverable SHA-1 filename alternative. Hash exceptions became the string `ERROR`; inaccessible directories could vanish silently. There was no cancellation, crash status, file stability check, queue, signature or authenticated clock proof. All scan work ran sequentially on the CLI thread.

## Changes

The entry point retains useful size/time helpers, legacy SHA-1 reading and original flag aliases. A Tkinter GUI was added because none existed. `dw/config.py` supplies validated versioned settings. `dw/windows.py` uses read-only ctypes APIs for drive discovery, file IDs, storage classification, journal querying/reading and hardware diagnostics. It imports no WMI/GPU libraries. GPU discovery runs as a bounded background PowerShell CIM query; its 32-bit VRAM estimate is explicitly qualified.

`dw/hashing.py` uses the official Rust-backed BLAKE3 package and hashlib SHA-256, a shared chunk loop for dual hashing, stable pre/post observations (including Windows open-handle ChangeTime) and a single retry. `dw/scanner.py` streams depth-first scandir iterators through a bounded producer queue and bounded worker futures. The background scan coordinator is the sole SQLite writer, uses executemany batches, commits every 2,000 rows or two seconds, and finalizes only after workers and inserts finish. WAL uses NORMAL durability in Quick/Verify and FULL in Forensic. NORMAL can lose recent commits after power failure; FULL requests stronger flushes. An OS lock prevents competing collectors from recovering a live scan. Startup of a database marks abandoned RUNNING records INTERRUPTED.

Live budgets control dispatched readers, BLAKE3 internal threads, queue depth and Quiet pacing. Small files use one internal BLAKE3 thread; a >=64 MiB task drains other readers before reserving several internal threads. Thread counts are capped. Lowering the slider drains in-flight work; no scan restarts. Conditional producer wakeups replaced polling delays found in profiling. Windows API bindings are cached. Context-managed evidence connections now close their handles, fixing retained WAL readers and Windows file locks.

Quick validates journal identity, volume identity and retention range, records changed IDs in a disk-backed temporary table, walks the selected namespace and rehashes dirty/new/renamed entries. A per-file USN guards against changes after the journal snapshot. Failed checks fall back to content verification. The saved checkpoint is the **start** snapshot so concurrent changes are replayed next time. Verify always reads accessible content; Forensic establishes both digests. Hard-link paths share identity; a stable per-object USN permits same-scan digest reuse, otherwise each path is independently read. Reparse targets are recorded and excluded. Inaccessible enumeration suppresses confident deletion and carries missing entries as UNVERIFIED.

`dw/evidence.py` owns additive v2 tables, streaming deterministic Merkle reduction, canonical manifests, Ed25519 signing and a validated timestamp-provider seam. Old compressed SHA-1 tables are not rewritten. Modern anonymization uses a user-supplied HMAC key and redacts persisted paths/progress/errors; the key is never saved in evidence. The GUI renders before hardware/settings probes, polls bounded messages and plots 100 rolling samples. CLI parity includes scan, list, capabilities, stored/live verify, export, compare, benchmark and migration. Dependencies changed from requests/pywin32 to blake3/cryptography/psutil; pytest is development-only.

## Validation and measured limits

See [PERFORMANCE_REPORT.md](PERFORMANCE_REPORT.md), machine-readable reports and the test suite. A GUI event-loop test verifies responsiveness under maximum-performance scanning. Real process-exit recovery, cancellation during Merkle finalization, live CLI workflows and database tampering are tested. USN permission failures and absent journals were observed on this Windows machine; valid continuity/rolloff/races are exercised with controlled fixtures, not claimed as an elevated full-volume acceptance test.

The measured mixed-file workload is metadata/identity-bound. SQLite is not its bottleneck. The modern collector performs substantially stronger checks than the old SHA-1 loop, so the old/new timings do not establish a speed improvement over legacy. The same modern workload does benefit from concurrency. The lightweight benchmark is bounded and may hit the OS cache; it does not prove raw storage saturation or tune every device.

## Remaining limits

There is no validated GPU hashing backend, configured RFC 3161 client, VSS snapshot, ADS collection or permission bypass. USN accelerates **content verification**, while namespace enumeration still visits the selected tree. Disk/GPU utilization and reliable remaining-time estimates are unavailable. Priority is not changed. The 64 MiB large-file threshold is configurable but remains an initial default; mmap is deliberately not enabled without suitable measurements. Benchmarks cache recommendations for review rather than silently applying overrides.

`--resume` retains interrupted evidence and starts a new pass; it does not splice partial scans into completed evidence. Logs are opt-in rotated JSON application diagnostics; evidence-relevant per-file errors live in SQLite. Scan roots protect file inventory and recorded metadata, not every operational event or byte of the SQLite container. Preserve signed manifests and pinned public keys externally. An already compromised endpoint, privileged tampering, undetectable concurrent mutations and operating-system access-time updates remain collection assumptions. No application can guarantee the absence of a physical resource bottleneck.
